# Developing the app

This file is for people who build or change the app. How to install and use it is in [README.md](README.md), written for riders who are not developers: it covers installing, connecting, troubleshooting and privacy, not the screens, which explain themselves; a change to any of those is described there too, in the rider's words.

OpenAMBike's app controls an Ampler e-bike over Bluetooth Low Energy, as [docs/protocol.md](../docs/protocol.md) specifies, with no server or account of its own; the Android app downloads only the map of a ride, from OpenFreeMap. It is an Ionic and Capacitor app built for Android and for the web.

The web build runs in browsers with Web Bluetooth: Chrome and Edge, on desktop and on Android, but not Firefox, nor Safari on iOS. It is a progressive web app that can be installed and works offline. The code stays cross-platform, so that someone with a Mac and an Apple developer account can add an iOS build; iOS is not built or tested.

## Running

You need Node 26 and, for Android, JDK 21 and the Android SDK with `platforms;android-36` and `build-tools;36.0.0`. Android Studio is not needed: the APK is built with Gradle on the command line and tried on a real phone. Run `npm install` once at the root of the repository, then, from the root:

| Command | What it does |
| --- | --- |
| `npm run dev --workspace=app` | Serve the app at http://localhost:8100; open it in Chrome or Edge on a computer with Bluetooth |
| `npm run build --workspace=app` | Build the web app into `app/dist/` |
| `npm run build --workspace=app && cd app && npx cap sync android && cd android && ./gradlew assembleDebug` | Build a debug APK |
| `cd app/android && ./gradlew :app:testDebugUnitTest` | Run the tests of the app's own Java code, on the computer |
| `adb install -r app/android/app/build/outputs/apk/debug/app-debug.apk` | Install the debug APK on a phone connected to ADB |
| `cd app && npx cap run android` | Build, install and start the debug app on a phone connected to ADB |

The debug APK is an app of its own, "OpenAMBike Debug", with an orange icon, with the application ID `io.github.rapsssito.openambike.debug`, so that it installs beside the release from F-Droid or GitHub (`io.github.rapsssito.openambike`) rather than over it. Each keeps its own owner key, settings and rides; only one may run auto-connect at a time, as only one app can hold the bike's connection.

The bike accepts one connection at a time: close the official app first. On Android, the first connection asks for the 6-digit code the bike shows, to pair. Then type the owner key once, or read it from a bug report ([docs/owner-key.md](../docs/owner-key.md) shows how to get it); the app keeps it on the device, and on Android connects to the same bike by itself each time it opens.

## Screens

A screen or control exists only for what the specification documents.

### Connect

With the owner key saved and, on Android, the bike known from an earlier connection, the app connects at once, with no button to press. Otherwise it asks for the key once per device (with a button that shows it), then finds the bike: on Android in the app's own list of bikes nearby, in a browser through the browser's chooser, which Web Bluetooth requires. The connection is shown step by step (connect, check the key, read the bike), and a failure as a message, with "Try again"; if the bike refuses a saved key, "Use another key" removes it, after a confirmation. Apart from the connection, under "Need your key?", "Read from a bug report" fills the key in from an Android bug report (the `.zip`, or a `btsnoop_hci.log` on its own), and "How do I get my key?" opens [docs/owner-key.md](https://github.com/Rapsssito/openambike/blob/main/docs/owner-key.md) in the system's browser. The disclaimer stays at the bottom of the screen. On Android, tapping the app's icon at the top five times within 3 seconds, while nothing connects, opens the signal test: every bike a scan hears in Android's fast scan mode, with its Bluetooth address, its signal strength now, and the average and number of readings of the last 5 seconds, until it is closed. It only listens to the bikes' advertising, so a bike shows only while no app is connected to it, and it sends nothing; it measures what auto-connect needs ([docs/roadmap.md](../docs/roadmap.md)). It is not shown to riders.

### Tabs

Once connected, four tabs, and on Android a fifth, Rides, each with the connection status in its header. When the link drops, the app stays on the tabs with the last values, shows "Reconnecting", greys out what would reach the bike, and connects again by itself until it succeeds; it goes back to the connect screen only when the rider disconnects, sends the bike to sleep or forgets the key, or the bike refuses the key.

- **Bike:** a first card split in two equal halves, a large figure in one and others in the other, in two views chosen at the top of the card; the card keeps one height in both views, and choosing a view changes only what it holds, nothing else on the page. Below it, the assist mode (off, mode 1, mode 2), and lights and lock as large tiles. Parked, for before a ride: a ring with the battery's charge, beside it the range and the odometer. Riding: the speed, large, with its unit under it, and in the other half motor power, rider power and the charge, each as its value over a horizontal bar, marked by an icon rather than a word (a flash for the motor, a person for the rider, a battery for the charge), with the word read by screen readers; the power bars fill up to 250 W, the rated power of a pedelec in the EU, and stay full above it, and the charge's bar turns to the warning colour at 20 % or less. There is no ring while riding, so that the speed is not read as a charge. The lock can be pressed in both views: locked while riding, the bike only stops assisting. The view switches to riding after 3 seconds of moving (above 3 km/h or with rider power), and back after a minute standing or with no figures from the bike, which sends none while it stands; the rider can switch it by hand until the next change. While the battery charges, the lights tile cannot be pressed and says why ([docs/protocol.md](../docs/protocol.md), "Lights").
- **Assist:** the assist speed (10 to 25 km/h) and assist amount (40 to 100 %) of each of the two modes, read from the bike and written back as [docs/protocol.md](../docs/protocol.md), "Commands sent to the bike", says for the assist levels. Both modes are saved together, in one write of the 6 bytes, with "Undo" and "Save" under them, half the width each; each mode's badge, at the top right of its card, alone says how it stands against the bike, with no other message on success: "Saved" while its sliders show the bike's values, "Not saved" once one is moved, with the bike's value beside the slider's own, small and struck through, and "Saving" while the bike takes them. Saving writes, then reads the levels back, again for up to a second while the bike still returns other values; they are "Saved" only once the bike returns what was written, otherwise a message says that the bike kept its values, which show beside the sliders. Undo puts the sliders back at the bike's values.
- **Battery:** every battery value the specification documents, live while connected: the charge as a ring, with an icon beside the value while the battery charges or discharges, and, while it charges only, a soft glint that sweeps along the filled arc from the start to the charge every few seconds; voltage, current and power; under "Health", the health and the charge cycles first, side by side, then as rows the temperature of each pack, the energy left (the absolute state of charge, in Wh) and the capacity when full; the battery firmware status. Health is measured against a rated capacity of 336 Wh, which every model of [docs/protocol.md](../docs/protocol.md), "Battery capacity by model", has; the bike does not say its model, and the rider can type another rating under "Health" (a whole number from 100 to 2 000 Wh), or go back to 336 Wh. The capacity when full is estimated as the energy left divided by the charge, shown above 30 % charge, where one percent is a small enough share for the estimate to hold; that the charge is relative to the battery's present capacity, as this estimate assumes, is not confirmed. Health is that capacity against the rated capacity, at most 100 %.
- **Rides** (Android only): the ride being recorded, with "Start ride", then "Pause" or "Resume" and "Stop ride" (confirmed first), and its moving time, distance and average speed, read again every 2 seconds; then the history, newest first, each ride with its date, distance and moving time, and "Export all". A ride records the phone's GPS, a fix a second, and the bike's ASI metrics and battery notifications whenever the bike is connected, through the app's native service, with the screen off or the app closed and a quiet notification. Its moving time leaves out the rider's pauses and every stop of 10 seconds or more with no speed or rider power from the bike and no GPS speed (auto-pause); its distance is the rise of the bike's odometer while connected, otherwise the GPS route, leaving out GPS drift while standing; the battery used is the fall of its absolute state of charge. Opened, a ride shows its route on a map, or, with no route, that the phone's location was off or not allowed while it was recorded, its figures (moving and total time, distance, average and top speed, average motor and rider power while moving, battery used), charts of its speed and of the motor's and the rider's power, "Export" and "Delete" (confirmed first). Exports are GPX 1.1, one track per ride, with Garmin's extension for speed, `power` for the rider's power as Strava reads it, and the motor's power in the app's own namespace, offered through Android's share menu. The history reads a ride's file once: the summary of a ride that ended is kept apart from the rides, in a folder of its own, and made again when the way it is made changes. A ride that auto-ride stopped ends at its last movement, so that its minutes standing are not part of it.
- **More:** bike information (firmware, motor controller firmware, battery serial number); settings (GPS, mobile network, units); "Automatic": auto-connect, auto-lock, auto-unlock and auto-ride, each a switch with an (i) beside its name that says what it does, auto-lock and auto-ride shown only with auto-connect on and auto-unlock only with auto-lock on; in the web app, all four are shown greyed out, and pressing one says that they need the Android app; on Android, and while auto-connect is on the connection's signal strength, read every 2 seconds, to check its thresholds; maintenance (restart, sleep, torque sensor calibration, each confirmed first); the encrypted export and import of the key; forgetting the key, confirmed first, which ends the connection; disconnecting; and "About": the app's version, its licence, a link to its source code, and the open-source licences of everything it ships. The factory motor calibration is not offered ([docs/safety.md](../docs/safety.md)).

### Auto-connect

Auto-connect, on Android, is kept and run by the app's native service (see "Structure"), so that it goes on with the app closed and after the phone restarts, with a notification while it is on, which Android requires; turning it on asks to show notifications. That notification is of Android's lowest importance, one folded line at the bottom of the notification shade with no sound and no icon in the status bar, and says only what auto-connect is doing: looking, connected with the bike locked or unlocked, or paused and why. The only notification that asks for attention is the warning that the bike may be unlocked. With the app on screen, it stands aside, and the app connects as it always does. In the background, it looks only for the bike last connected, filtered by its address, in Android's low-power scan mode, and in the fast mode once it hears it above −72 dBm; it connects once the bike's signal has averaged above −72 dBm for 10 seconds, about 1.5 m with the phone in a pocket ([docs/protocol.md](../docs/protocol.md), "Advertising"), and takes over the app's connection when the app leaves the screen. Connected, it reads the connection's signal strength twice a second and lets go once that has averaged below −80 dBm for 3 seconds, about 4 to 5 m, early enough to lock before the link drops at walking pace with the rider's body between phone and bike, and also once the bike has reported no movement (no non-zero motor power, speed or rider power in ASI metrics) for 15 minutes, after which it pauses, which its notification then says, until the app is opened or the bike has not been heard above −80 dBm for a minute, the rider having left: the bike advertises whenever no device is connected to it, except in deep sleep ([docs/protocol.md](../docs/protocol.md), "Advertising"), so it keeps a low-power scan for that alone. With auto-lock on, it locks the bike before it lets go, unless the bike is already locked, and never while the bike reported movement in the last 30 seconds, so that the assistance never stops under a rider; if the connection drops before it could lock, or the lock fails, a notification says that the bike may be unlocked. With auto-unlock on, offered only with auto-lock and confirmed when turned on, a connection it made because the phone came near unlocks the bike if it is locked; nothing else unlocks it ([docs/safety.md](../docs/safety.md), "What the project never does"). A lock pressed in the app holds: once the rider locks the bike by hand, auto-unlock skips every arrival until the rider unlocks it by hand, and auto-lock still locks on leaving whatever the rider pressed. Disconnecting in the app, or sending the bike to sleep, pauses auto-connect until the rider connects again, which the Disconnect row ("Disconnect and pause auto-connect") and then the connect screen say while auto-connect is on; forgetting the key, or the bike refusing it, turns it off. Each connection sends the service the texts of the app's language and the key the bike accepted. Its settings survive an update of the app that changes what the service needs: auto-connect shows as on, and waits for the app's next connection to send them again in the new form.

### Auto-ride

Auto-ride, on Android and offered only with auto-connect, starts a ride by itself once the bike has reported movement, as auto-connect reads it, for 20 seconds within 30, whoever holds the connection, so that wheeling the bike out does not start one. It stops the rides it started once neither the bike nor the GPS has shown movement for 15 minutes, as long as auto-connect waits before it lets a parked bike go, or as soon as auto-connect lets the bike go; a ride started by hand is stopped by hand. Once the rider stops a ride by hand, auto-ride starts none until the bike has stood still for 15 minutes or auto-connect let it go. Turning it on asks for location "all the time", since it starts recording with the app closed; without it, a ride started with the app not on screen records the bike's figures and no route. While auto-ride is on without it, as after Android takes back the permissions of an app left unused, or the rider turns it off in Android's settings, More shows a warning under auto-ride with "Allow", checked again each time the app comes back on screen; and when a restored backup turns auto-ride on again at the first connection, the app asks for it at once, saying why.

### Changes to the bike

No control shows a change before the bike has made it. Pressed, a control that changes the bike (assist mode, lights, lock, GPS, mobile network) keeps showing the bike's last value, cannot be pressed again and shows a spinner, until the bike notifies the value asked for; only then does it show it. If the bike does not notify it within 5 seconds, as with the lights while it charges, or the link drops first, the control stays as it was and a message says why. Saving an assist mode waits for the levels the bike returns. Restart, sleep and torque sensor calibration wait only for the write, since what the bike notifies after them is not yet known ([docs/roadmap.md](../docs/roadmap.md)).

## Stack

- JavaScript, not TypeScript: ES modules with types written in JSDoc and checked by `tsc` (`checkJs`, `strict`), so that every file runs as written and is still type-checked.
- Ionic's web components (`@ionic/core`) used directly as custom elements, with no UI framework; pages and state are plain modules. Vite bundles the web build, and Capacitor wraps it for Android.
- npm, with a root `package.json` that holds the tools (TypeScript, oxlint, oxfmt, Jest, husky, commitlint, semantic-release and its plugins) and `app/` as an npm workspace that holds the app's own dependencies. Versions are exact (`.npmrc`); Node's version is the one `.nvmrc` names.
- Interface in English and Spanish, every text in translation files, so that other owners can add their languages.
- BLE in the web build through `@capacitor-community/bluetooth-le`, which uses Web Bluetooth. Whether the bike's passkey pairing works through Web Bluetooth on each system: **Unknown**. In the Android build, through the app's own Capacitor plugin, BikeLink, whose service holds the link to the bike, so that later the link can outlive the app's screen ([docs/roadmap.md](../docs/roadmap.md)); it knows nothing of the protocol and moves the bytes `src/ble/bike.js` gives it. The community plugin's Android code still ships, unused, since Capacitor adds every plugin the web build needs.
- Maps through MapLibre GL JS (BSD-3-Clause), with OpenFreeMap's vector tiles, which are free and need no account or key; MapLibre is loaded only when a ride is shown.
- A feature that needs a platform API checks for it and is hidden where it is missing: auto-connect, auto-ride and rides exist only on Android, where the app's native service runs them; the web build shows the automatic options greyed out, saying they need the Android app, and has no Rides tab.
- The owner key is typed or imported once per device and kept there; it is saved only after the bike accepts it. On Android, it is kept in the Android Keystore (AES-GCM) through `@aparajita/capacitor-secure-storage`, and a copy, as plain text, in the shared preferences `owner-key-backup.xml`, for Android's backup alone, since the Keystore's key never leaves the phone; when the Keystore holds no key, as on a restored phone, the app takes the copy and saves it in the Keystore again. Forgetting the key removes both. In the web build, it is kept in the origin's IndexedDB, encrypted with AES-GCM under a non-extractable Web Crypto key kept beside it. The browser's storage never holds the owner key as plain text, and the encryption key cannot be read out, though code running on the app's own origin could still use it. No passphrase is asked to connect.
- The encrypted export, for a backup or another device, is a JSON text with the format name `openambike-owner-key`, version 1, and the owner key encrypted with AES-GCM, with its salt and IV. The AES key is derived from a passphrase of at least 8 characters with PBKDF2-SHA-256 and 600 000 iterations.
- Application ID: `io.github.rapsssito.openambike`, the form F-Droid accepts for a project hosted on GitHub that owns no domain; the Java package (`namespace`) stays `org.openambike.app`, as it does not identify the app. Display name: OpenAMBike.

## Structure

- `src/ble/protocol.js`: encoding and decoding of the bike's values, pure functions with no BLE or UI dependency, so that tests run on captured frames alone. Its tests use anonymised frames from captures, each naming the capture it comes from.
- `src/ble/bike.js`: scanning, connection, authentication, a queue that sends one request at a time, and subscription to notifications.
- `src/ble/native-client.js`: the BikeLink plugin offered with the same methods as the community plugin, which `src/ble/bike.js` uses on Android; bytes cross the bridge as hexadecimal text.
- `src/session.js`: a connected bike and everything known about it, read at the start and kept live by the bike's notifications; paused, with its values kept, while the link is down. Screens read its state and call its commands; they never talk to the bike directly.
- `src/connection.js`: reconnecting when the link drops: connect, check the key and start the session again, retrying after 1, 2, then every 5 seconds, until it succeeds or the bike refuses the key.
- `src/battery-health.js`: the default rated capacity, the one every model of [docs/protocol.md](../docs/protocol.md), "Battery capacity by model", has, and the estimate of the battery's capacity and health.
- `src/rides/`: rides. `ride.js` reads a ride's file as it grows and sums it up, decoding the bike's bytes with `src/ble/protocol.js`; `gpx.js` writes rides as GPX; `rides.js` asks the native service to start, pause and stop, lists, reads and deletes rides, and exports them; `route-map.js` draws a route with MapLibre from OpenFreeMap, loaded the first time a ride is shown.
- `src/auto-connect.js`: what the native service needs to run auto-connect, prepared from `src/ble/protocol.js` and the translation files (the owner key, the lock, the bytes that say the bike moves, the thresholds, the notifications' texts), and the calls the screens make to turn it on, off or pause it.
- `src/preferences.js`: the units, the rated capacity if the rider typed one, and on Android the identifier of the last bike connected (its Bluetooth address), kept in the browser's storage so that the app reaches the bike again with no scan.
- `src/storage/key-store.js`: where the owner key is kept on this device, as "Stack" says.
- `src/storage/key-export.js`: the encrypted export and import, so that the key can be moved to a new phone or kept as a backup.
- `src/bug-report/`: the owner key read from an Android bug report, as `reverse-engineering/tools/owner_key.py` reads it: `zip.js` takes the snoop logs out of the `.zip` with the browser's own `DecompressionStream`, reading only the parts it needs; `owner-key.js` finds in them the key the bike answered `owner ok` to. Everything stays in memory on the device, and only the key is kept, once the bike accepts it. It is offered wherever `DecompressionStream` exists.
- `src/pages/`: one module per screen, built from the elements of `ui.js`; `errors.js` turns Bluetooth's and the bike's errors into the user's words, and `ride-mode.js` tells from the bike's figures whether it is being ridden.
- `src/i18n/`: the translation files, one per language, with the same keys.
- `src/test-support/`: a fake Bluetooth client that behaves like the bike, for the tests.
- `scripts/licences.js`: the licences the "Open-source licences" screen shows, collected when the app is built (see "Libraries and licences").
- `scripts/release.js`: what a release adds to semantic-release: the Android version, the texts of the release page and of `CHANGELOG.md` beside the changes, and F-Droid's changes of the version, as "Build and release" says.
- `android/`: the Android project Capacitor generates, with the app's permissions and backup rules, and the app's own Java code in `app/src/main/java/org/openambike/app/`: in `link/`, `BikeLink` (scanning, bonding, the connection, and one GATT operation at a time on its own thread), `BikeLinkService` (the service that holds it, and runs auto-connect as a foreground service), `AutoConnect` and `AutoRide` (auto-connect's and auto-ride's decisions, with no Android code, so that they are tested on their own), `AutoConnectConfig` (what `src/auto-connect.js` prepared), `SecretStore` (that configuration, owner key included, encrypted with AES-GCM under an Android Keystore key, in a file outside backups), `RideRecorder` (a ride written as it happens, one JSON object per line: start, GPS fixes, the bike's notifications of the characteristics asked for, undecoded, pauses, stop; in the app's own files, under `rides/`), `BootReceiver` (auto-connect again after the phone restarts) and `BikeLinkPlugin` (the bridge to the JavaScript), with their tests in `app/src/test/`.

## Design

The app aims to be attractive and easy, built from a few simple, reusable interface elements.

- Ionic's iOS look on every platform, so that the app looks the same on Android and in a browser. The app's own palette, defined once in `src/theme.css` for light and dark, follows the system's dark mode. Nothing of Ampler's look is used ([docs/safety.md](../docs/safety.md), "Name and trademark").
- What a rider uses most comes first and largest: battery, speed, assist mode, lights and lock are on the first tab, as large tiles one tap away.
- Each screen has at most one primary action. A change to the bike that is hard to undo (restart, sleep, calibration, forgetting the key) is confirmed first, with a sentence on what it does.
- Every value shows its unit, and a state is shown by text or an icon as well as by colour. Touch targets are at least 44 px. Texts are short and come from the translation files.
- The reusable elements live in `src/pages/ui.js` (card, section, gauge, stat, toggle tile, choice, value row, action row, dialogs and messages); screens compose them and add no styling of their own beyond layout.
- Screenshots taken to review the design are low-resolution: a phone-size viewport of 360 × 720 at 1× scale, saved as JPEG.

## Icon

`public/icon.svg` is the app's icon: an open wheel rim with its hub, and a dot passing through the opening, white on the app's green (`#0f9d76`). It is the web app's favicon and the image at the top of the repository's README. The Android launcher icon is made from it: `android/app/src/main/res/drawable/ic_launcher_foreground.xml` holds the same shapes, on the background colour of `values/ic_launcher_background.xml`. The PNGs beside it are rendered from the SVG and change when it does: `mipmap-*/ic_launcher.png` (the rounded square) and `ic_launcher_round.png` (on a circle) at 48, 72, 96, 144 and 192 px from mdpi to xxxhdpi, and every `drawable*/splash.png`, the glyph at 35 % of the shorter side on the green, at each file's own size. The debug build's icon is the same on orange (`#e8590c`), so that it is told from the release installed beside it: `android/app/src/debug/res/` holds its background colour and its `mipmap-*` PNGs, rendered the same way.

## Permissions

- **Android 12 and later:** `BLUETOOTH_SCAN` (with `neverForLocation`) and `BLUETOOTH_CONNECT`.
- **Earlier versions:** location, which Android needs there to scan, and the legacy `BLUETOOTH` and `BLUETOOTH_ADMIN`, limited to them with `maxSdkVersion` 30.
- **Rides:** `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION`, asked when the first ride starts, to record its route, and `FOREGROUND_SERVICE_LOCATION`, for the service that records it with the app closed. Started from the screen, a ride needs location only while using the app; `ACCESS_BACKGROUND_LOCATION` ("all the time") is asked only when auto-ride is turned on, for the rides it starts with the app closed.
- **Auto-connect:** `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_CONNECTED_DEVICE`, for the service that runs it; `POST_NOTIFICATIONS`, asked from Android 13 when auto-connect is turned on, for its notifications; `RECEIVE_BOOT_COMPLETED`, to run it again after the phone restarts.
- **`INTERNET`:** only for the map of a ride, drawn with MapLibre from OpenFreeMap's tiles, which are downloaded only while a ride is shown and tell OpenFreeMap the phone's IP address and the area shown. The app talks to no server of its own. The link to the owner key guide opens in the system's browser, not in the app.
- **Android backup holds the rides, the owner key and the automatic options:** `allowBackup` is true, and the backup rules (`backup_rules.xml` before Android 12, `data_extraction_rules.xml` from it) include only `rides/`, `ride-summaries/` and the shared preferences `owner-key-backup.xml` and `auto-connect.xml`, which leaves everything else out; the cloud backup only when it is encrypted end to end with the phone's screen lock, the copy to a new phone always. `owner-key-backup.xml` is the owner key's copy for the backup (see "Stack"): protected by that encryption and, on the phone, by Android's app sandbox only, not the Keystore. `auto-connect.xml` holds the automatic options as the rider set them (auto-connect on, auto-lock, auto-unlock, auto-ride) and whether the rider's lock holds; auto-connect's settings stay in `SecretStore`, outside backups, since its Android Keystore key never leaves the phone. After a restore, the app connects with the key from the backup, and that first connection turns auto-connect on again with those options.

## Build and release

- The web build is served over HTTPS, since Web Bluetooth needs a secure context; `localhost` counts as one.
- Releases are made by [semantic-release](https://semantic-release.gitbook.io/) (`release.config.js`), which `.github/workflows/release.yml` runs after the checks when it is started by hand on `main` (the Actions tab, "Release", "Run workflow"). The Conventional Commits since the last release decide the version: `fix` makes a patch release, `feat` a minor one, a breaking change a major one, and other types none.
- A release writes its version to `android/app/version.properties` (`versionName` the version, `versionCode` major × 1 000 000 + minor × 1 000 + patch, from `scripts/release.js`), builds the signed APK, adds the release notes to the top of `CHANGELOG.md` at the root, commits both files as `chore(release): <version>`, tags the commit `v<version>`, and attaches `OpenAMBike-<version>.apk` to a [GitHub release](https://github.com/Rapsssito/openambike/releases). The release page lists the changes, then says that the app is unofficial ([docs/safety.md](../docs/safety.md), "Name and trademark") and how to install it; `CHANGELOG.md` says it once, under its title, above every release's changes.
- The APK is signed with the project's own key, which never enters the repository. The build reads it from `OPENAMBIKE_KEYSTORE` (the keystore's path), `OPENAMBIKE_KEYSTORE_PASSWORD`, `OPENAMBIKE_SIGNING_ALIAS` and `OPENAMBIKE_KEY_PASSWORD`; without them, `./gradlew assembleRelease` builds an unsigned APK. The workflow takes them from the repository's secrets `ANDROID_KEYSTORE_BASE64` (the keystore in base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`, and refuses to release without them. No variable that holds something public, such as the alias, has `key`, `token`, `password` or `secret` in its name: semantic-release hides the values of those variables in everything it writes, the release notes included. Every release is signed with the same key, so that each installs over the last: losing the key means that owners have to uninstall the app, and with it the stored owner key, to install a new one.
- The Android build has nothing F-Droid refuses: no Google services, and no dependency metadata in the APK (`dependenciesInfo`).
- F-Droid publishes the project's own signed APK, so that owners can move between F-Droid and the GitHub releases without reinstalling. Its recipe, `metadata/io.github.rapsssito.openambike.yml` in [fdroiddata](https://gitlab.com/fdroid/fdroiddata), builds each new `v<version>` tag unsigned, with the same commands as the release (`npm ci`, the web build, `cap sync`, `assembleRelease`), and publishes the APK of the GitHub release only if it is identical to that build apart from the signature, and is signed with the project's key. A new tag is found by F-Droid's bot, which reads `versionCode` and `versionName` from `android/app/version.properties` in it, so nothing is done by hand per release; it may take a few days.
- The build is therefore reproducible: the same tag gives the same APK on any machine and in any folder, with Node 26 and JDK 21. A change that breaks that (a timestamp, an absolute path or an unordered list in a built file, a different Node or JDK) stops F-Droid's updates until it is fixed. To check a release, build its tag unsigned in a fresh clone in another folder, as above, and compare: `apksigcopier compare OpenAMBike-<version>.apk --unsigned app-release-unsigned.apk` prints nothing when they match. A change of build commands or tool versions is made in the recipe too.
- F-Droid's listing is in `fastlane/metadata/android/` at the root: the title, the short and the full description, which state that the app is unofficial ([docs/safety.md](../docs/safety.md), "Name and trademark"), and in `changelogs/<versionCode>.txt` each release's changes in plain text, at most 500 characters, which the release writes from its notes (`scripts/release.js`) and commits with the version. F-Droid takes the icon from the APK.

## Libraries and licences

Before a library is added to the app, its licence is read at its source and must be compatible with the app's licence, AGPL-3.0. A library that phones home, shows ads or tracks usage is not used.

The app shows the licence of everything it ships under More, "About", "Open-source licences": its own (the repository's `LICENSE`), and every package of its production dependencies with the licence file the package ships (or, for a package that ships none, the licence section of its README), collected by `scripts/licences.js` when the app is built. The Android libraries that Gradle adds, which npm does not list (AndroidX, the Kotlin standard library and Apache Cordova's Android framework, all under the Apache License 2.0, whose text is in `scripts/apache-2.0.txt`), are named in `ANDROID_LIBRARIES` in that file, which changes when a `build.gradle` gains or loses a library.
